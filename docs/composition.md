# 合成

[Necoherence の概要](../README.md)

用語の定義は [用語索引](terminology.md#合成) を、各言語の関数名は各言語の README を参照してください。

## 探索結果

合成の探索の結果は次のいずれかです。

- `Solved`: 検証済みの導出木
- `Unreachable`: 到達不能 ( 閉包を返す )
- `Incomplete`: 未解決の条件が残存
- `Ambiguous`: 複数の導出候補が存在し一意に定まらない

## 合成の検証

### 検証対象

括弧内は `Necoherence.SemanticComposition` における Lean の定義名です。

- 型の包含: ある型のすべての値が別の型にも含まれることを示す証明データ ( `verifyInclusion` )
- 空の型: 値の集合が空である型の判定 ( `verifyEmptyTypes` )
- 反例: 包含元の型に属するが、包含先の型で拒否される値の検出 ( `verifyCounterexample` )
- 合成入力の検証: 関数シグネチャ群、初期入力、目標の妥当性検査と、探索用入力の準備 ( `prepareDirectComposition` )
- 入力束縛: 関数の入力ポートへ渡す値の組み立て ( `checkBinding` )
- リソース軌跡: 計画の各分岐におけるリソース消費を型付き遷移モデルへ写像した、到達および非循環の証明データ ( `verifyResourceTrace` )
- 候補計画: 導出計画と、その計画が型制約および分岐条件を満たすことの証明のペア ( `verifyCompositionCandidate` )
- 閉包: 初期状態から探索された状態集合が、後続状態に対して閉じていることの証明データ ( `verifyCompositionClosure` )
- 合成: 計画と証拠の組である候補と、その候補を選んだ選択根拠の妥当性判定 ( `verifyComposition` )

### 選択根拠

選択根拠 ( `SelectionEvidence` ) として「実行可能な任意の計画を許容する方針」または「閉包内で正規計画が一意に定まることの証明」のいずれかを指定します。選択根拠のキーは、規則 `canonicalPlanKey` に従って計画から生成する文字列であり、Lean の導出木を復号する時と、合成ソルバーの導出木を復号する時に再計算します。

### 正規計画

計画に基づいて規則 `canonicalPlanKey` で正規計画を識別するキーを計算します。ガード条件を持たず、リソースを読み取り専用で参照し、生成リソースが空である純粋関数を直列に呼び出す計画の場合、キーは関数呼び出しの集合によって決まります。それ以外の計画では、呼び出し順序も含めてキーを決定します。

### 検証の結果

検証に成功すると、検証済みの値を返します。ここでは、Lean の実装では検証条件の証明をフィールドに持ち、これに対して Rust の実装では検証関数を通してのみ構築できます。この検証関数は、合成のソルバーの crate にあります。

- crate: `necoherence-composition-solver`
- 関数: `necoherence_composition_solver::verification::verify_composition`

## 合成の実行

導出木は合成のソルバーが作り、ソルバーは作った合成を自身の検証関数で確かめます。これに対して、Lean の定義は導出木を直接検証し、Rust のコード生成ツールは受け入れ検証 ( 詳細は [generation.md](generation.md) を参照 ) を行います。実行の関数は 6 言語すべての実装に備わっており、Lean 実装には検証を通過した合成 ( `CheckedComposition` ) を、他の 5 言語の実装には受け入れ検証の結果から得た合成を渡します。

### 実行の入力

実行の開始には、次の値を渡します。

- 合成: 実装ごとの型は下表のとおり
- 宣言した関数ごとの実装 ( `Provider` ) の一覧
- 初期入力の値
- ネットワーク副作用の状態

ここで、Lean 実装には照合して準備した合成問題 ( `PreparedCompositionInput` ) と検証を通過した合成 ( `CheckedComposition` ) を渡します。他の 5 言語の合成には、準備した合成問題と計画が含まれます。

| 実装 | 実行の開始が受け取る合成 | 合成の取得方法 |
| --- | --- | --- |
| Lean | `CheckedComposition` | 検証を通過した合成 |
| Rust | `PreparedRun` | 受け入れ検証の結果から得た合成で作る ( [Rust の README](../packages/rust/adapter/README.md#合成の実行) を参照 ) |
| Python | `AdmittedComposition` | 受け入れ検証の結果の `admitted_composition` |
| TypeScript | `AdmittedComposition` | 受け入れ検証の結果の `composition` |
| Java | `AdmittedComposition` | 受け入れ検証の結果の `composition()` |
| Gleam | `CheckedComposition` | 受け入れ検証の結果から `semantic_signatures.checked_composition` で得る |

### 関数の実装

合成は関数のシグネチャだけを持つため、実行には宣言した関数ごとの実装 ( `Provider` ) を呼び出し元が渡します。実装は宣言した各関数に 1 つずつ用意し、その種類を関数の作用宣言と一致させます。

- 純粋関数用: 引数を受け取り、呼び出しの結果を同期的に返す
- HTTP 用: HTTP リクエストを送る関数の実装

#### HTTP 用の実装

通信用の実装は、引数からリクエストを準備する処理と、レスポンスをデコードする処理を持ちます。準備の処理は、送信準備完了 ( `ready` ) または事前完了 ( `completed` ) を返します。

通信用の実装が「送信準備完了」を返すと、送信の指示を含む保留状態が返されます。呼び出し元は指示に従って通信し、得られた観測結果を再開の関数 ( `resume` ) に渡します。これに対して「事前完了」を返した場合は通信を行わず、その結果を用いて計画の次の段階へ進みます。

送信の指示と観測は、[機能](operations.md#ネットワーク副作用の指示と観測) を参照してください。

### 進捗状態

実行の結果は、進捗状態または実行時エラーです。進捗状態は次のいずれかです。

- 完了: 実行結果とネットワーク副作用の最終状態。実行結果は、目標の出力値または宣言された失敗
- 保留: 現在の実行状態と、次に行うべきネットワーク副作用の指示 ( サスペンド )

### 実行時エラー

実行時エラーは、エラー要因 ( `ExecutionFailure` ) とネットワーク副作用の状態の組 ( `RunFailure` ) です。

主なエラー要因:

- 引数の不足
- 関数の実装の不足、または宣言した関数と実装の対応の不一致
- 宣言されていない結果の返却
- 関数の実装で発生したエラー
- ネットワーク副作用の障害
